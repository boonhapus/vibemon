# Lifecycle transitions gate on asset existence, not orchestrator timing

`born → christened → manifested` advances only when the AssetRefs required for that state are present in Monstore. State is therefore derivable and idempotent: a partial christen that crashes mid-upload can be re-run safely, and no separate workflow log is needed to recover. Full manifestation is deferred until a Vibemon must become battle-ready or fully presented, because candidates can be reviewed with cheaper preview assets but wild encounters and owned battle presentation need battle sprites from the manifested sheet. Rejected wild candidates and encounter-supply generations therefore enter the wild pool as christened and are manifested lazily during prewarm or encounter preparation. Background prewarming should opportunistically manifest likely wild encounter candidates; if a cold candidate is selected, the encounter reveal, such as a silhouette slide-in, hides generation latency before battle presentation starts. Adoption and release preserve any existing core manifestation assets instead of regenerating or degrading them; trainer-personalized cosmetics, if introduced later, should be separate assets. The rejected alternative — timestamp-driven workflow states advanced by the orchestrator — coupled state correctness to the orchestrator's runtime guarantees and made replays fragile. See `app/lifecycle/vibemon.py`.
